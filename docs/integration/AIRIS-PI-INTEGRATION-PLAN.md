## 1. Layer boundaries

```
airis-monorepo/
├── vendor/pi/                 UPSTREAM RUNTIME LAYER  — do not hand-edit
│   ├── packages/              12 upstream packages, original names, own lockfile
│   ├── apps/                  upstream apps (p2, p2-mac, p3)
│   ├── scripts/  tsconfig.base.json  vitest.base.ts  biome.json
│   ├── package.json  package-lock.json   ← upstream's own, used verbatim
│   ├── LICENSE  README.md  AGENTS.md  SECURITY.md  CONTRIBUTING.md
│   └── UPSTREAM.md            pinned commit + date
├── packages/                  AIRIS PRODUCT LAYER — existing, unchanged
│   ├── ai/  agent/  coding-agent/  tui/       (@sufiyan-sabeel/airis-*)
│   └── (future) airis-runtime/                adapter, not yet created
├── backend/  crates/  website/  airis-web-deploy/  tools/  demo/  docs/  scripts/
└── package.json               AIRIS workspaces — vendor/pi is NOT a member
```

### Why `vendor/pi` and not `packages/`

Two reasons, both concrete:

1. **Directory collision.** AIRIS already owns `packages/ai`, `packages/agent`, `packages/coding-agent` and `packages/tui`. Pi's packages use the same directory names. Vendoring into `packages/` would require renaming or deleting AIRIS's own packages first — forbidden by the preservation rules.
2. **The npm arborist bug.** Adding `vendor/pi/packages/*` to AIRIS's workspaces crashes npm 10.9.4 during peer-set resolution (`Cannot read properties of null (reading 'edgesOut')` in `#loadPeerSet`, on `vendor/pi/packages/agent/node_modules/vitest`). Isolating the tree avoids both the crash and 12 upstream workspaces re-resolving inside AIRIS's lockfile.

### Isolation rules

- `vendor/pi` keeps **upstream's own `package.json` and `package-lock.json`** and is installed with `npm ci` inside its own directory. It is never a member of AIRIS's workspaces.
- AIRIS's repository checks (`check:pinned-deps`, `check:ts-imports`) skip `vendor/` — upstream follows upstream conventions, and policing it with AIRIS policy would produce thousands of false failures. Biome already scoped its includes to `packages/*`.
- AIRIS's `tsconfig.json` does not include `vendor/`.
- No global rename of upstream package imports. Upstream names stay `@earendil-works/*`.

## 4. Known upstream build characteristics

Two properties of the upstream tree that the integration must account for — both discovered by attempting the build, not assumed:

1. **`packages/ai/src/providers/data/` is gitignored upstream** and generated by `npm run hydrate:model-data`, which fetches over the network. A fresh clone of Pi cannot build `ai` until that runs. The `pi-runtime` workflow therefore hydrates before building.
2. **`chord` is large** (879 TypeScript files) and its build exceeds a 2 GB container. It builds on a normal CI runner.

Neither is a defect in the vendoring; both are properties of upstream that a consumer must plan for.
